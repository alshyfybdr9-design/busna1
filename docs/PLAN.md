# باصنا — النقل المدرسي: البنية وخطة التنفيذ

## نتيجة فحص المشروع (المرحلة الأولى)
المستودع `busna1` كان فارغًا تمامًا عند البدء (بدون أي commit). لا توجد بنية سابقة لباصنا يمكن إعادة استخدامها،
لذلك تم اعتماد البناء من الصفر بموافقة صاحب المشروع، باستخدام **Next.js + Supabase**، وتصميم البنية لتكون أساس منصة باصنا
متعددة المنتجات (النقل المدرسي هو أول وحدة).

## البنية

```
busna1/
├─ supabase/
│  ├─ migrations/      ← المخطط، RLS، محرك الرحلات، نماذج القراءة
│  ├─ seed.sql         ← بيانات تجريبية عربية (مدرستان لاختبار العزل)
│  └─ tests/           ← اختبارات الأمان وتدفق الرحلة (تعمل على PostgreSQL عادي)
├─ apps/web/           ← Next.js: لوحة المدرسة + تطبيقات السائق/المشرف/ولي الأمر (PWA)
└─ docs/
```

### تعدد المستأجرين (Multi-Tenancy)
- **المستأجر = المدرسة** (`schools`). كل سجل يحمل `school_id`.
- **مفاتيح أجنبية مركّبة `(id, school_id)`**: يستحيل على مستوى قاعدة البيانات أن يشير سجل في مدرسة إلى سجل في مدرسة أخرى
  (مثلًا ربط طالب بباص مدرسة أخرى يفشل بخطأ FK حتى لو تجاوز أحدهم الواجهة).
- **RLS على كل الجداول**، والدوال المساعدة في مخطط `private` غير المكشوف عبر API.
- جداول الرحلات (الحالة، الحضور، المواقع، الأحداث، الإشعارات) **لا تقبل الكتابة المباشرة** من العميل إطلاقًا؛
  كل تغيير يمر عبر دوال RPC تتحقق من الدور والحالة.

### الأدوار
| الدور | المصدر | الصلاحيات |
|---|---|---|
| مشغّل المنصة | `platform_admins` | إنشاء المدارس (`create_school`) |
| مالك / مدير | `school_members` | إدارة كاملة لبيانات مدرسته فقط |
| مشاهد | `school_members(viewer)` | قراءة فقط |
| سائق | `staff(driver)` | رحلاته فقط: بدء، حضور، وصول، إنهاء، إرسال الموقع |
| مشرف | `staff(supervisor)` | رحلاته فقط: حضور، ملاحظات، بلاغات، **أرقام أولياء الأمور** |
| ولي أمر | `guardians` | أبناؤه فقط؛ موقع الباص **فقط** أثناء وجود ابنه داخله في رحلة نشطة |

- السائق **لا يرى** أرقام أولياء الأمور (لا يتصل أثناء القيادة) — التواصل من صلاحيات المشرف.
- ولي الأمر **لا يرى** نقاط توقف الرحلة (مواقع منازل طلاب آخرين)، ولا سجل أحداث الرحلة، ولا مسار الباص قبل صعود ابنه.
- ربط الحساب: الإدارة تُنشئ سجل السائق/ولي الأمر برقم الجوال، وعند تسجيل الدخول برقم **موثّق** يُربط تلقائيًا (`claim_my_records`).

### آلة حالات الرحلة
```
scheduled ──start_trip──▶ started ──(أول موقع/صعود)──▶ in_progress ──end_trip──▶ completed
    │                                                     │
    └──────────────cancel_trip (إدارة فقط)──────────────▶ cancelled
```
- **التأخير** و**الطوارئ** أعلام مستقلة (`delay_minutes`, `emergency_active`) لأن الرحلة قد تكون "جارية" و"متأخرة" معًا.
- **الوصول للمدرسة ≠ إنهاء الرحلة**: `arrive_trip` يسجّل الوصول ويُنزل كل من على متن الباص صباحًا ويُشعر أولياء الأمور؛
  `end_trip` يغلق الرحلة ويوقف التتبع، ويرفض الإغلاق إذا بقي طالب داخل الباص، ويطلب تأكيدًا صريحًا لتسجيل غير المعالَجين غائبين.
- حالات الطالب: `pending → boarded → dropped` أو `pending → absent`، مع تراجع محدود (تصحيح خطأ) ونقرات مكررة آمنة.
- كل إجراء يُسجَّل في `trip_events` مع الفاعل ودوره والوقت والموقع.

### التتبع المباشر
- الموقع يُرسل من جهاز السائق عبر `push_locations` على دفعات (يدعم الطابور عند انقطاع الإنترنت).
- الخادم **يرفض** أي موقع خارج رحلة نشطة (`trip_not_active`) فيتوقف التطبيق عن المشاركة.
- `bus_live_positions`: صف واحد لكل رحلة نشطة (يُحذف عند الإنهاء) ← Supabase Realtime.
- `bus_locations`: سجل المسار (جاهز للتقسيم الشهري Partitioning عند التوسع).
- إشعار "الباص يقترب" يُحسب في الخادم من المسافة الفعلية (مرة واحدة لكل طالب).

### الإشعارات
تُنشأ من الأحداث الفعلية فقط داخل نفس المعاملة (transaction): بدء الرحلة، الاقتراب، الصعود، الوصول للمدرسة،
الإنزال عند المنزل، الغياب، التأخير، الإلغاء، الطوارئ. مع منع التكرار. التوصيل (Push/SMS) يتم عبر عامل خلفي
يقرأ `delivery_status = 'pending'`.

### مساعدو الذكاء الاصطناعي
- يعملان بأدوات (tools) تستدعي قاعدة البيانات **بجلسة المستخدم نفسه** — فالـ RLS يمنع تلقائيًا الوصول لبيانات الغير.
- لا يخترعان مواقع أو أوقات: وقت الوصول المقدّر يُحسب فقط من موقع حديث فعلي ويُعرض كتقدير.
- أي تعديل يقترحه مساعد الإدارة يُحفظ في `ai_action_proposals` ولا يُنفّذ إلا بموافقة صريحة (`decide_ai_proposal`).

## التشغيل

### 1) مشروع Supabase
```bash
supabase link --project-ref <PROJECT_REF>
supabase db push            # يطبّق supabase/migrations
```
- **Auth → Providers**: فعّل Phone (مزوّد SMS مثل Twilio أو Unifonic) وEmail.
- **Database → Extensions**: فعّل `pg_cron` لإنشاء رحلات اليوم تلقائيًا (أو شغّل `private.generate_trips_all_schools()` من جدولة خارجية).
- بيانات تجريبية للتطوير المحلي فقط: `supabase/seed.sql` (كلمة المرور لكل الحسابات: `Busna@12345`).

### 2) تطبيق الويب
```bash
cp apps/web/.env.example apps/web/.env.local   # ثم عبّئ القيم
pnpm install
pnpm dev
```
| المتغير | الوصف |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | من إعدادات API في Supabase |
| `NEXT_PUBLIC_MAP_STYLE_URL` | نمط الخريطة (افتراضيًا OpenFreeMap بدون مفتاح) |
| `ANTHROPIC_API_KEY` | لتفعيل المساعدين الذكيين (خادم فقط) |

### 3) إنشاء مدرسة (عميل جديد)
يسجّل مالك المدرسة حسابًا بالبريد، ثم ينفّذ مشغّل المنصة (`platform_admins`):
```sql
select public.create_school('al-fajr', 'مدارس الفجر', 'owner@school.sa', 'الدمام');
```
بعدها يضيف المالك الباصات والطاقم والطلاب (أو يستوردهم من Excel) من لوحة المدرسة.
