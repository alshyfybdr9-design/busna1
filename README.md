# باصنا — Busna

منصة متعددة الجهات (Multi-tenant SaaS) لإدارة النقل المدرسي: لوحة ويب للمنصة وللجهات، وتطبيق جوال موحد للسائق وولي الأمر مع تتبع موقع حقيقي في الخلفية.

> **الحالة: المرحلة 1 مكتملة** — المسار الأساسي يعمل من البداية للنهاية:
> إضافة طالب ← تعيينه لباص ومسار ← بدء رحلة ← تسجيل الصعود والنزول ← متابعة ولي الأمر ← إنهاء الرحلة وفحص خلو الباص.

---

> **للتجربة السريعة بأمر واحد عبر Docker: راجع [START-HERE.md](START-HERE.md).**

## الحزمة التقنية ولماذا

| الجزء | التقنية | السبب |
|---|---|---|
| قاعدة البيانات | PostgreSQL 14+ مع Row Level Security | عزل الجهات والأدوار **داخل قاعدة البيانات نفسها**، لا في الكود فقط |
| الخادم | Node.js 22 + TypeScript + Fastify 5 + `pg` + Zod | سريع، تحقق صارم من المدخلات، SQL صريح يسهل تدقيقه |
| لوحة الويب | React 19 + Vite + React Query + Leaflet | RTL كامل، مزود خرائط قابل للتبديل |
| تطبيق الجوال | Expo SDK 58 (React Native) + expo-location + expo-task-manager + expo-sqlite | **تتبع خلفي أصلي** (Foreground Service على أندرويد، Background Location على iOS)؛ ليس PWA |

لا يوجد Supabase؛ سياسات RLS مكتوبة يدويًا ومُختبرة على Postgres حقيقي.

## بنية المستودع

```
db/migrations/        ترحيلات SQL (المخطط، RLS، عمليات الرحلة)
apps/api/             خادم الـ API + العامل الخلفي + الاختبارات
apps/web/             لوحة الويب (المنصة + الجهات)
apps/mobile/          تطبيق Expo (السائق + ولي الأمر) — مشروع npm مستقل
```

## نموذج الأمان باختصار

- **ثلاثة أدوار اتصال بقاعدة البيانات**: `busna_app` (طلبات المستخدمين، يخضع لـ RLS)، `busna_auth` (المصادقة فقط)، `busna_worker` (المهام الخلفية). كل دور بصلاحيات جداول محدودة. لا يُستخدم `BYPASSRLS`.
- كل طلب يُنفّذ داخل معاملة تضبط `app.tenant_id / app.user_id / app.role` من **الجلسة الموثقة في الخادم**؛ الدور والجهة يُقرآن من جدول العضويات في كل طلب (إيقاف العضوية يسري فورًا).
- ولي الأمر يرى أبناءه فقط، ونقطة توقف أبنائه فقط (لا منازل الآخرين)، وموقع الباص **أثناء رحلة جارية فقط**.
- السائق يرى ويعدّل رحلاته فقط؛ محفّز في القاعدة يمنعه من تعديل خطة الرحلة أو القفز بين الحالات.
- رابط/رمز الجهة يعرض الاسم والشعار فقط. الدعوات: رمز عشوائي لمرة واحدة، مخزّن كبصمة SHA-256، له صلاحية، ومقيد بالبريد/الجوال المدعو إن حُدد.
- كلمات المرور بـ scrypt، قفل مؤقت بعد 5 محاولات، رموز وصول قصيرة (15 د) ورموز تحديث مُدوّرة مع كشف إعادة الاستخدام.
- سجل تدقيق (إضافة فقط) للتعديلات الحساسة: الطلاب، الأعضاء، الدعوات، التصحيحات، الإلغاء، الإعدادات، التنبيهات.

## التشغيل محليًا

المتطلبات: Node.js 20+، PostgreSQL 14+.

```bash
cp .env.example .env
```

ولّد `JWT_SECRET` وضعه في `.env`:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

```bash
npm install
```

```bash
npm run db:bootstrap
```

```bash
SEED_PASSWORD='Demo-pass-2026' npm run db:seed
```

```bash
npm run dev:api
```

```bash
npm run dev:web
```

- الويب: http://localhost:5173 — جرّب رمز الجهة `DEMO01` أو الرابط `/t/DEMO01`.
- حسابات تجريبية (كلها بكلمة المرور أعلاه): `admin@demo.busna.local`، `supervisor@…`، `driver1@…`، `driver2@…`، `parent1@…`، `parent2@…`، `platform@demo.busna.local`.
- كل البيانات التجريبية موسومة `[تجريبي]` و`is_demo=true`، وسكربت البذر يرفض العمل في الإنتاج.

إنشاء مدير منصة حقيقي (كلمة مرور مؤقتة تُطبع مرة واحدة):

```bash
npm -w apps/api run admin:create -- --email you@example.com --name "اسمك"
```

### الإنتاج (قاعدة البيانات)
1. أنشئ قاعدة البيانات والأدوار `busna_owner` و`busna_app` و`busna_auth` و`busna_worker` بكلمات مرور قوية عبر أدوات مزود قاعدة البيانات (الأسماء الثلاثة الأخيرة ثابتة لأن سياسات RLS تشير إليها). فعّل امتدادي `citext` و`pgcrypto`.
2. شغّل الترحيلات فقط بـ `DATABASE_OWNER_URL`:

```bash
npm run db:migrate
```

3. الخادم يستخدم `DATABASE_APP_URL` و`DATABASE_AUTH_URL` و`DATABASE_WORKER_URL` فقط — لا يحتاج اتصال المالك.

## الاختبارات

```bash
npm test
```

تُنشئ قاعدة `busna_test` منفصلة من الصفر في كل تشغيل. **النتيجة الحالية: 35/35 ناجحة**، وتشمل:

| المطلوب | الاختبار |
|---|---|
| منع ولي أمر من بيانات طفل غير مرتبط | API (404) + اتصال مباشر بدور `busna_app` (RLS) |
| منع الوصول بين جهتين | API + محاولة قراءة/كتابة بمعرّف مزوّر على مستوى RLS |
| منع السائق من تحديث رحلة غير معيّنة | سائق آخر في نفس الجهة وسائق جهة أخرى + محفّز القاعدة |
| عدم تكرار الصعود/النزول بعد إعادة المزامنة | نفس `clientEventId` مرتين = سجل واحد |
| ظهور قِدم بيانات الموقع | `ageSeconds` و`isStale` بعد تقادم النقاط |
| توقف التتبع بعد الانتهاء | رفض نقاط الموقع (409) وإخفاؤه عن ولي الأمر |
| منع نزول بلا صعود | رفض `not_boarded` + تصحيح بصلاحية وسبب محفوظ في التدقيق |
| تصعيد الحالات غير المحسومة | تنبيه حرج للمشرف عند إنهاء رحلة بطالب لم ينزل |
| الإشعارات | بلا تكرار، ونص شاشة القفل لا يحتوي اسم الطفل |
| المصادقة | قفل الحساب، تدوير الرموز وكشف إعادة الاستخدام، اختيار السياق، الدعوات لمرة واحدة |

تحقق إضافي أُجري: مسار كامل عبر واجهة الويب الحقيقية بـ Playwright (إضافة طالب ← تعيين ← إنشاء رحلة ← سائق عبر الـ API ← لوحة حية ← إنهاء وفحص)، و`tsc` نظيف للمشاريع الثلاثة، و`expo export` يبني حزم Android وiOS بنجاح.

## ما يتطلب إعدادًا خارجيًا (غير مُفعّل حاليًا)

| التكامل | الحالة | ما المطلوب منك |
|---|---|---|
| إشعارات الجوال (Push) | الكود جاهز (Expo Push)؛ الإشعارات تُحفظ داخل التطبيق دائمًا | حساب Expo/EAS و`extra.eas.projectId`، مفاتيح FCM (أندرويد) وAPNs (iOS)، ثم `PUSH_PROVIDER=expo` |
| بناء التطبيق ونشره | لم يُبنَ أو يُختبر على جهاز حقيقي | حساب Expo، حساب Apple Developer وGoogle Play، معرّفات الحزم الحقيقية بدل `com.example.busna` |
| الروابط العامة (Universal/App Links) | قوالب في `apps/web/public/.well-known/` | نطاق حقيقي بدل `app.busna.example`، Team ID من Apple، بصمة شهادة التوقيع لأندرويد |
| بلاطات الخرائط | الافتراضي خوادم OSM العامة (**للتطوير فقط** وفق سياسة استخدامها) | مزود تجاري أو استضافة ذاتية عبر `VITE_MAP_TILE_URL` |
| وقت الوصول التقديري | معطّل عمدًا (`ROUTING_PROVIDER=none`) — يُعرض "غير متاح" | مزود توجيه (OSRM ذاتي، Google Routes، Mapbox) — الواجهة `EtaProvider` جاهزة |
| إرسال الدعوات بالبريد/SMS | الروابط تُنسخ وتُشارك يدويًا | مزود بريد (SES/SendGrid…) ومزود SMS؛ ويُوصى بتحقق OTP |
| بوابة الدفع | المرحلة 2 | حساب بوابة لكل جهة (مثل Moyasar/HyperPay/Tap) |
| الذكاء الاصطناعي | المرحلة 3 | مفتاح مزود النموذج (يُخزن في الخادم فقط) |

## القيود المعروفة (بصراحة)

- **تطبيق الجوال لم يُشغَّل على جهاز أو محاكٍ** في بيئة البناء هذه: تم التحقق بالـ typecheck وتجميع الحزم ومراجعة الإعدادات الأصلية فقط. يجب اختباره ميدانيًا (التتبع مع قفل الشاشة، وضع توفير البطارية، فقدان الشبكة) قبل الاستخدام الفعلي.
- خريطة ولي الأمر داخل التطبيق: حاليًا زر "عرض على الخريطة" يفتح تطبيق الخرائط بالإحداثيات. خريطة مدمجة (react-native-maps) تحتاج مفتاح Google Maps لأندرويد — مرحلة لاحقة.
- التحديث الحي في اللوحة وتطبيق ولي الأمر بالاستطلاع الدوري (10–20 ث)، لا WebSocket.
- فحص خلو الباص **إقرار من السائق** وليس دليلًا مستقلًا؛ متوفر: مسح ملصق QR في مؤخرة الباص (اختياري/إلزامي حسب الجهة)، وتأكيد تحقق مستقل من موظف ثانٍ، وتنبيه تلقائي عند تأخر الفحص.
- لا توجد مصادقة ثنائية (MFA) لمديري المنصة بعد — أولوية في المرحلة 2.
- رمز التحديث في الويب محفوظ في `localStorage`؛ الأفضل في الإنتاج ملف تعريف ارتباط `HttpOnly`.
- تواريخ "اليوم" تستخدم منطقة الجهة الزمنية، لكن بعض فحوص قاعدة البيانات (مثل إلغاء الغياب) تستخدم تاريخ الخادم.
- لا يوجد نظام نسخ احتياطي مُعدّ (انظر أدناه).

## الاحتفاظ بالبيانات والنسخ الاحتياطي

- إحداثيات الباص: تُحذف بعد `locationRetentionDays` (افتراضي 30 يومًا، قابل للضبط لكل جهة) — يشغّله العامل الخلفي تلقائيًا كل ساعة تقريبًا، أو يدويًا:

```bash
npm -w apps/api run worker:retention
```

- الإشعارات: تُحذف بعد 180 يومًا. سجلات الحضور والتدقيق محفوظة (سجلات تشغيلية).
- النسخ الاحتياطي (مطلوب منك): فعّل النسخ الآلي ونقطة الاستعادة الزمنية (PITR) لدى مزود Postgres، واختبر الاستعادة دوريًا. نسخة يدوية:

```bash
pg_dump --format=custom --file=busna-$(date +%F).dump "$DATABASE_OWNER_URL"
```

## خطة المراحل التالية

- **المرحلة 2 — الرسوم والمدفوعات والإشعارات**: خطط رسوم النقل، الاستحقاقات، حالات (مدفوع/معلق/متأخر/مسترد)، إيصالات، تكامل بوابة مستقل لكل جهة مع تحقق خادمي من Webhooks الموقعة ومعالجة التكرار، تصدير التقارير، تفعيل Push، MFA لمديري المنصة، الوصول الاستثنائي المبرر والمسجل لدعم المنصة، اشتراكات المنصة وحدود الاستخدام.
- **المرحلة 3 — الدعم و«مساعد باصنا»**: تذاكر دعم موجهة للجهة الصحيحة (المنصة مقابل الجهة)، المساعد بأدوات خادم محددة النطاق (`get_active_trip`، `get_latest_allowed_bus_location`، `submit_absence_request`، `create_support_ticket`، `escalate_to_human`…) تعمل عبر نفس طبقة RLS، مزود نموذج قابل للاستبدال، حدود تكلفة لكل جهة، سياسة احتفاظ للمحادثات، وبقاء الدعم التقليدي عند تعطل النموذج.
- **المرحلة 4 — التشغيل**: خريطة مدمجة في التطبيق، WebSocket/SSE، مزود ETA، تقسيم جدول المواقع زمنيًا، مراقبة وتنبيهات بنية تحتية.
