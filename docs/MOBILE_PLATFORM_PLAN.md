# باصنا — خطة التطبيق الموحّد وتعدد شركات النقل

> الهدف: تطبيق جوال واحد (React Native) على iOS وAndroid يخدم **السائق/المشرف، ولي الأمر، والطالب الجامعي**،
> ولوحتا ويب: **لوحة شركة النقل** و**لوحة باصنا الرئيسية**، مع دعم عدة شركات نقل بعزل بيانات كامل وهوية (شعار وألوان) لكل شركة
> — بدون إعادة بناء المشروع الحالي.

## 1. ما الذي نعيد استخدامه (الوضع الحالي)

المنطق كله تقريبًا داخل PostgreSQL (Supabase) كدوال RPC محمية بـ RLS، والواجهة الحالية طبقة رقيقة فوقها.
هذا يعني أن **تطبيق الجوال يستدعي نفس الدوال الموجودة** ولا يحتاج خادمًا جديدًا:

| الموجود | يستخدمه تطبيق الجوال كما هو |
|---|---|
| `start_trip` / `arrive_trip` / `end_trip` / `report_delay` / `report_incident` | واجهة السائق |
| `push_locations` (دفعات، طابور عدم اتصال، يرفض خارج الرحلة النشطة) | التتبع في الخلفية |
| `record_attendance` + **`record_attendance_by_qr`** (أُضيفت الآن) | الحضور بالمسح |
| `parent_overview` / `parent_tracking` + Realtime | ولي الأمر والطالب |
| جدول `notifications` (يُنشأ من الأحداث الفعلية، مع `delivery_status`) | الإشعارات |
| `my_access` | توجيه الواجهة حسب الدور بعد الدخول |

اختبارات قاعدة البيانات (`supabase/tests`) تغطي العزل والصلاحيات وتدفق الرحلة، وتعمل كلها بنجاح.

## 2. البنية المستهدفة

```
busna1/
├─ apps/web/        ← لوحة شركة النقل (/admin) + لوحة باصنا الرئيسية (/platform — جديدة)   [Next.js، موجود]
├─ apps/mobile/     ← تطبيق Expo / React Native الموحّد                                     [جديد]
├─ packages/core/   ← أنواع قاعدة البيانات المولّدة، عميل Supabase، رموز الأخطاء، تنسيق، QR   [جديد، مشترك]
└─ supabase/
   ├─ migrations/   ← المصدر الوحيد لمنطق الأعمال والصلاحيات
   └─ functions/    ← Edge Functions: توصيل الإشعارات، الدفع، Webhooks                     [جديد]
```

- `packages/core` يُستخرج من `apps/web/src/lib` (types، errors، format، student-qr) ويُستبدل `lib/types.ts`
  المكتوب يدويًا بأنواع مولّدة من `supabase gen types` حتى لا يختلف الكود عن قاعدة البيانات.

## 3. تعدد المستأجرين: من «مدرسة» إلى «شركة نقل»

**الوضع الحالي:** المستأجر = `schools`، وكل جدول يحمل `school_id`، والعزل مطبّق في قاعدة البيانات (RLS + مفاتيح أجنبية مركّبة).

**المطلوب:** المستأجر = **شركة نقل**، والشركة تخدم **جهات** (مدارس، جامعات، فروع).

```
باصنا (platform_admins)
 └─ شركة نقل  (organizations)        ← المستأجر: الشعار، الألوان، الأسعار، حساب الدفع
     └─ جهة   (institutions)          ← مدرسة / جامعة / فرع، لها موقع ووقت دوام
         └─ طلاب، مسارات، رحلات
```

**طريقة التنفيذ (تدريجيًا، بدون كسر الموجود):**
1. جدول `institutions (id, org_id, kind: school|university, name, lat, lng, timezone, settings)`.
2. إضافة `institution_id` إلى `students` و`routes` و`trips` بمفتاح مركّب `(institution_id, org_id)` يمنع الربط بين شركتين.
3. ترحيل البيانات: كل «مدرسة» حالية تصبح شركة + جهة واحدة بنفس الاسم → المدارس التي تشغّل باصاتها بنفسها تبقى تعمل كما هي.
4. التسمية: `schools → organizations` و`school_id → org_id`. **إن لم توجد قاعدة بيانات إنتاجية بعد** فالأسهل تعديل ملفات
   الـ migrations مباشرة الآن (9 ملفات)؛ وإن وُجدت فنُبقي اسم العمود ونغيّر المفهوم فقط (انظر القرارات في §10).
5. الهوية لكل شركة: `logo_url` و`primary_color` موجودة؛ التطبيق يقرأها بعد الدخول ويطبّق الثيم وقت التشغيل.
   **تطبيق واحد في المتاجر باسم «باصنا»** — لا حاجة لتطبيق منفصل لكل شركة. المستخدم المرتبط بأكثر من شركة يرى مبدّل شركات.
6. الطالب الجامعي: حساب خاص به (`students.user_id`) يتتبع باصه ويدفع اشتراكه ويعرض رمز QR الخاص به.

## 4. التطبيق الموحّد (Expo / React Native)

- **Expo + Expo Router + TypeScript**، والبناء والنشر عبر EAS، مع تحديثات فورية (OTA) للإصلاحات السريعة.
- **الدخول:** رقم الجوال + رمز تحقق (Supabase Auth)، والجلسة محفوظة في `expo-secure-store`.
- **التوجيه حسب الدور:** بعد الدخول نستدعي `my_access` ← مجموعات مسارات `(driver)` و`(parent)` و`(student)`. من له أكثر من دور يختار.
- **العربية:** `I18nManager.forceRTL(true)` وخط IBM Plex Sans Arabic.
- **الخرائط:** `@maplibre/maplibre-react-native` مع نفس مصدر الخرائط الحالي (OpenFreeMap، بدون مفتاح).

### السائق — GPS في الخلفية
| الخيار | المزايا | العيوب |
|---|---|---|
| `expo-location` + `expo-task-manager` | مجاني ومدعوم من Expo | أقل مقاومة لقتل التطبيقات من بعض أجهزة أندرويد |
| `react-native-background-geolocation` (Transistorsoft) | الأقوى: كشف الحركة، طابور SQLite، توفير البطارية | ترخيص مدفوع لنسخة أندرويد |

**التوصية:** نبدأ بـ `expo-location` ونختبره ميدانيًا (قفل الشاشة ساعة، انقطاع الشبكة، أجهزة Samsung/Xiaomi)، وننتقل للمدفوع إذا فشل.
- التتبع يبدأ مع `start_trip` ويتوقف تلقائيًا عند `trip_not_active` (منطق موجود في الخادم).
- النقاط تُحفظ محليًا ثم تُرسل على دفعات عبر `push_locations` الموجودة (تحفظ وقت الـ GPS الأصلي).
- أندرويد: Foreground Service بإشعار ظاهر «جارٍ مشاركة موقع الباص». iOS: صلاحية «دائمًا» + `UIBackgroundModes: location`.
- **المتاجر:** Google Play يطلب نموذج إفصاح عن الموقع في الخلفية مع فيديو، وApple تطلب تبريرًا واضحًا. صلاحية الخلفية تُطلب **للسائق فقط**.

### الحضور بـ QR
- مسح بطاقة الطالب بـ `expo-camera` ← `record_attendance_by_qr` (جاهزة ومختبرة).
- بدون إنترنت: المسح يُحفظ في طابور ويُعاد إرساله بوقته الأصلي (نفس فكرة `lib/outbox.ts`).
- الطالب الجامعي: QR متغيّر داخل التطبيق (صلاحيته قصيرة) لمنع مشاركة البطاقة — مرحلة لاحقة.

## 5. الإشعارات خارج التطبيق

1. جدول `device_tokens (user_id, expo_push_token, platform, updated_at)`.
2. Database Webhook عند إضافة سجل في `notifications` ← Edge Function `deliver-notification`:
   - إشعار جوال عبر Expo Push (يوصل إلى APNs وFCM).
   - رسالة SMS عبر **Unifonic** لمن فعّل `notify_sms`، أو للأحداث الحرجة (الطوارئ والغياب).
   - تحديث `delivery_status` و`delivered_at`.
3. `pg_cron` يعيد محاولة الإشعارات المعلّقة. واتساب لاحقًا عبر قوالب WhatsApp Business.

## 6. الاشتراكات والدفع

**مستويان:**
- (أ) **ولي الأمر / الطالب ← شركة النقل** (رسوم النقل): هذا في النسخة الأولى.
- (ب) **شركة النقل ← باصنا** (اشتراك المنصة): في البداية بفواتير يدوية من لوحة باصنا.

**الجداول:**
- `plans (org_id, name, period, price_halalas, vat_rate, trip_kind: one_way|two_way, institution_id?)`
- `subscriptions (org_id, student_id, payer_user_id, plan_id, status: pending_payment|active|past_due|cancelled|expired, starts_on, ends_on)`
- `invoices (org_id, number, subtotal, vat, total, status, due_on)` بترقيم متسلسل لكل شركة
- `payments (invoice_id, provider, provider_payment_id unique, amount, status, raw jsonb)`

**الربط بالتشغيل:** إنشاء رحلات اليوم يضم فقط الطلاب الذين لديهم اشتراك نشط (مع فترة سماح من إعدادات الشركة).

**بوابة الدفع: Moyasar** (مدى، Apple Pay، STC Pay، البطاقات):
1. التطبيق يطلب الدفع من Edge Function `create-payment`. المبلغ يُحسب في الخادم من الفاتورة، ولا يُقبل من التطبيق أبدًا.
2. شاشة الدفع من Moyasar أو Apple Pay داخل التطبيق.
3. Webhook `moyasar-webhook` يتحقق من التوقيع ويعيد جلب الدفعة من Moyasar، ثم يعلّم الفاتورة مدفوعة ويفعّل الاشتراك.
- **المتاجر:** النقل خدمة تُستهلك خارج التطبيق، فالدفع عبر بوابة خارجية مسموح (لا يلزم الشراء داخل التطبيق من Apple/Google).
- **الفوترة الإلكترونية (ZATCA / فاتورة):** مطلوبة للشركات المسجلة في ضريبة القيمة المضافة؛ نجهّز الحقول الآن والتكامل لاحقًا.

## 7. لوحات الويب
- **لوحة شركة النقل** = `/admin/[slug]` الحالية، ونضيف لها: الجهات، الخطط والأسعار، الاشتراكات، الفواتير والمدفوعات، وتصفية حسب الجهة.
- **لوحة باصنا الرئيسية** `/platform` (لـ `platform_admins`): إنشاء الشركات (بدل SQL اليدوي)، الخطط، الفوترة، المتابعة والدعم.

## 8. إصلاحات أمنية قبل الإطلاق (من فحص 2026-11-07)
- `claim_my_records`: ربط الحساب بالإيميل يمكن استغلاله إذا كان تأكيد البريد معطّلًا ← نستبدله برمز دعوة أو التحقق بالجوال فقط.
- حدود استخدام (Rate limit) لمسارات المساعد الذكي وتسجيل الدخول برسائل SMS.
- إغلاق ثغرة إعادة التوجيه بعد الدخول (`next=//…`).
- فهارس للمفاتيح الأجنبية في الاستعلامات الكثيرة، وتقسيم جدول `bus_locations` مع سياسة احتفاظ بالبيانات.
- استبدال `xlsx` من npm بنسخة مُصلحة.

كل مرحلة تنتهي باختبارات قاعدة البيانات واختبار ميداني على أجهزة حقيقية.

## 10. قرارات تحتاج موافقة صاحب المشروع
1. **هل توجد قاعدة بيانات إنتاجية فيها بيانات حقيقية؟** يحدد هل نعيد تسمية المخطط مباشرة أو بترحيل تدريجي.
2. **من يستلم أموال الاشتراكات؟** حساب Moyasar مستقل لكل شركة نقل (موصى به)، أو تحصّل باصنا ثم تحوّل للشركات (يحتاج ترتيبات نظامية).
3. **مكتبة GPS في الخلفية:** المجانية أولًا (موصى به) أو المدفوعة من البداية.
4. **مزوّد الرسائل:** Unifonic؟ وهل نحتاج واتساب في النسخة الأولى؟
5. **تسعير الطالب الجامعي:** خطة مستقلة لكل جهة أم أسعار موحّدة للشركة؟
